## 1. 이번 단계에서 만든 것

### 1.1 기능 범위

| 구분 | 구현 | 다음 단계로 미룸 |

| 대사·품질 | 원천↔집계 대사 6종, 잔액 연속성 점검, 잔액 누락 점검, 전체 데이터 상태 판정 | — |
| 기초자료 | 중도매인, 영업 상태 이력, 담당 경매사(기간), 담보·보증·한도 **버전 + 승인**, 보증인(별도 저장소), 증빙 업로드 | 서식 연결(2단계) |
| 조회 | 통합 홈(1단계 항목), 중도매인 통합 상세(기준일로 보기 포함), 가져오기·오류 점검, 사용자·권한, 변경·처리 이력 | 채권·동향·실적 대시보드(2~3단계) |
| 운영 | 단계별 정기 처리·실패 시 이어서 재실행, 실행시간 분할, 백업·복구, 공유 상태 점검 | 알림(2단계) |

### 1.2 적용한 가정 (설계 v0.1 → v0.2 반영)

| 질문 | 적용한 가정 | 코드 위치 |
|---|---|---|
| Q1 운영 환경 | 개인 계정 + 가상 데이터 PoC. 웹앱은 "나만 접근"으로 배포 | `appsscript.json` (`access: MYSELF`) |
| Q2 원천 자료 | 월 단위 CSV 3종, 마지막 줄 `#CONTROL,행수,금액합계` | `Config.gs` `SOURCE_SPEC` |
| Q3 내부 규정 | 연체는 원천 제공값 그대로, 한도는 유형별 표시·합산 안 함, 한도 사용률·회전율은 산출하지 않음 | `Api.gs` `build360_` 안내 문구 |
| Q4 승인 체계 | 시스템 내 단일 승인(관리자), 요청자 본인 승인 금지 | `Master.gs` `decideVersion_` |
| Q5 규모·조회 범위 | 경매사는 담당 중도매인만 조회, 채권담당·관리자·조회자는 전체 | `Logic.gs` `canAccessWs_` |

설계 v0.1에서 바뀐 점: 1단계에서는 업무 저장소 `DB_WORK`(신호·관리 건)를 만들지 않는다(2단계에서 추가). 그래서 저장소는 5개다.

## 2. 파일별 역할

```
wholesaler-system/
├─ gas/                      ← Apps Script 프로젝트에 그대로 올리는 파일
│  ├─ appsscript.json        매니페스트(시간대·권한 범위·웹앱 배포 설정)
│  ├─ Config.gs              설정값, 저장소·시트·컬럼 스키마, 원천 파일 형식
│  ├─ Logic.gs               공통 업무 로직(순수 함수): CSV·검증·집계·대사·데이터 상태·버전·권한표·실적 비교
│  ├─ Db.gs                  시트 읽기/쓰기, 행 버전 충돌 검사, 잠금
│  ├─ Audit.gs               변경 이력·접근 기록·작업 로그
│  ├─ Auth.gs                사용자 식별, 서버 측 권한 확인(apiCall_), 편집기 전용 함수 보호
│  ├─ Setup.gs               초기 설정(폴더·저장소·시트), 공유 상태 점검, 트리거 설치
│  ├─ Pipeline.gs            정기 처리: 가져오기→집계→대사→상태, 실패 시 상태 보존·이어서 실행
│  ├─ Backup.gs              일 백업·보관 정리·복구
│  ├─ Master.gs              기초자료 업무 로직(등록·버전·승인·담당·사용자·증빙)
│  ├─ Api.gs                 웹앱 공개 함수(api_*)와 화면 데이터 조립(통합 상세·홈)
│  ├─ Main.gs                웹앱 진입점(doGet)
│  ├─ VirtualData.gs         가상 데이터 생성기(같은 seed → 같은 자료)
│  ├─ TestData.gs            가상 데이터 적재, 운영 중 점검(runPhase1Checks)
│  ├─ Index.html / Styles.html / Client.html   화면
├─ tests/
│  ├─ gas_mock.js            Apps Script 서비스 모의 구현(로컬 검증용)
│  ├─ run_tests.js           1단계 검증 시나리오 77개
│  └─ render_ui.js           헤드리스 브라우저로 화면 열기·캡처·스크립트 오류 확인
└─ docs/
   ├─ 01_설계안_v0.1.md
   ├─ 02_1단계_구현안내.md   (이 문서)
   └─ 03_1단계_검증결과.txt  run_tests.js 실행 결과
```

함수 이름 규칙: 이름이 `_`로 끝나는 함수는 비공개 함수라 웹 화면(`google.script.run`)에서 호출할 수 없다. 공개 함수는 웹앱용 `api_*`와 편집기 실행용(`setupSystem`, `runPipeline` 등)뿐이다. 편집기 실행용은 첫 줄에서 소유 계정인지 확인한다.

## 3. 저장소·시트 구조

`setupSystem` 이 Drive에 `중도매인통합관리` 폴더와 아래 파일을 만든다. 파일 ID는 스크립트 속성(`DBID_*`, `FOLDER_*`)에 저장된다.

| 저장소 파일 | 시트 | 한 행의 의미 | 사람이 직접 편집 |
|---|---|---|---|
| `DB_MASTER` 기초 | `M_WHOLESALER` | 중도매인 1명의 현재 기본정보 | 불가(웹앱으로만) |
| | `M_WS_STATUS_HIST` | 기간별 영업 상태 | 〃 |
| | `M_ASSIGNMENT` | 기간별 담당 경매사 (권한 판정에 사용) | 〃 |
| | `M_CONTACT` | 업무 연락처 1개 | 〃 |
| | `M_COLLATERAL` / `M_GUARANTEE` / `M_LIMIT` | 담보·보증·한도 1건의 **특정 버전** (유효기간 + 승인 상태) | 〃 |
| | `M_EVIDENCE` | 증빙 파일 1개(파일 ID·해시) | 〃 |
| | `M_USER` | 사용자 1명(이메일·역할·상태) | 〃 |
| | `M_CALENDAR` | 하루(경매일 여부) | 〃 |
| `DB_PII` 민감 | `P_GUARANTOR` | 보증인 1명(최소 항목) | 불가 |
| `DB_RAW` 원천 | `R_BATCH` | 파일 1회 가져오기(해시·건수·관리합계·상태) | 불가(추가만) |
| | `R_SALES` / `R_RECEIPT` / `R_AR_BAL` | 원천 1행 + 행 키·내용 해시 | 〃 |
| | `R_REJECT` | 거부된 원천 행 1개(오류 코드·원문) | 〃 |
| `DB_AGG` 집계 | `A_DAILY` / `A_MONTHLY` | 중도매인×일(월)×부류(과일/채소/전체) | 불가(매번 재생성) |
| | `A_RECON` | 대사 결과 1항목 | 〃 |
| | `A_DQ` | 데이터 이상 1건(누락·불일치·경고) | 〃 |
| | `A_STATUS` | 최신 기준일·데이터 상태 등 키-값 | 〃 |
| `DB_LOG` 이력 | `L_AUDIT` / `L_ACCESS` / `L_JOB` | 변경 1회 / 거부·민감 조회 1회 / 작업 1회 | 불가(추가만) |

- 컬럼 정의는 `Config.gs` `SCHEMA` 가 유일한 기준이다. 날짜·문자 컬럼은 텍스트 서식으로 만들어 Sheets 자동 날짜 변환을 막는다.
- 집계 시트(`DB_AGG`)는 언제든 원천에서 다시 만들 수 있으므로 손상되면 `runPipeline` 만 다시 실행하면 된다.

### 원천 CSV 형식 (UTF-8, 첫 줄 헤더)

| 파일명 접두어 | 헤더 | 행 키 | 같은 키·다른 내용 |
|---|---|---|---|
| `SALES_` | `source_txn_no,line_no,txn_date,wholesaler_id,category,amount,txn_type,correction_type,orig_txn_no` | 거래번호+행번호 | 거부(정정은 새 거래번호 + 원거래번호) |
| `RECEIPT_` | `source_receipt_no,receipt_date,posted_date,wholesaler_id,amount,receipt_type` | 입금번호 | 거부 |
| `AR_BAL_` | `base_date,wholesaler_id,balance,overdue_amount,max_overdue_days` | 기준일+중도매인 | 수정본으로 추가 적재, 최신 배치 우선 |

마지막 줄: `#CONTROL,<데이터 행 수>,<금액 합계>` (잔액 파일은 잔액 합계). 원천 시스템의 실제 추출 형식이 정해지면 `SOURCE_SPEC` 과 `validateRow_` 만 바꾸면 된다. **[확인 필요]**

## 4. 초기 설정 방법

### 4.1 Apps Script 프로젝트 만들기 (둘 중 하나)

**방법 A — 편집기에 붙여넣기**
1. https://script.google.com → 새 프로젝트 → 이름 `중도매인 통합관리`.
2. 프로젝트 설정 → "편집기에 'appsscript.json' 매니페스트 파일 표시" 켜기 → `gas/appsscript.json` 내용으로 바꾸기.
3. `gas/` 의 `.gs` 파일마다 같은 이름의 스크립트 파일을 만들어 내용을 붙여넣는다(`Code.gs` 는 지운다).
4. `Index`, `Styles`, `Client` HTML 파일을 만들어 같은 내용을 붙여넣는다.

**방법 B — clasp(명령줄)**
```bash
npm install -g @google/clasp
clasp login
cd wholesaler-system/gas
clasp create --type standalone --title "중도매인 통합관리" --rootDir .
clasp push
```

### 4.2 실행 순서 (편집기 상단 함수 선택 → 실행)

| 순서 | 함수 | 하는 일 | 처음 실행 시 |
|---|---|---|---|
| 1 | `setupSystem` | 폴더·저장소 5개·시트 생성, 실행한 계정을 관리자로 등록 | Google 권한 동의 화면이 나온다 |
| 2 | `loadVirtualData` | 가상 기초자료 적재 + 원천 CSV 75개를 `01_가져오기_대기`에 생성 (어제까지 25개월) | 기초자료가 이미 있으면 거부 |
| 3 | `runPipeline` | 가져오기·집계·대사 | 6분을 넘길 것 같으면 스스로 나눠 1분 뒤 이어서 실행 |
| 4 | `runPhase1Checks` | 운영 자료를 훼손하지 않는 점검(시나리오 3·4·7·8·9) | 실행 로그에 통과/실패 표시 |
| 5 | `checkSecurity` | 저장소·폴더가 비공개인지 확인 | 경고가 있으면 공유 해제 |
| 6 | `installTriggers` | 매일 06시 정기 처리, 02시 백업 [가정] | |

실제 자료로 운영할 때는 2번을 건너뛰고, 웹앱의 기초자료 화면에서 등록하거나(소량) 별도 이관 절차로 넣는다(조직 승인 후).

## 5. 배포·권한 설정

### 5.1 웹앱 배포
1. 편집기 → 배포 → 새 배포 → 유형: 웹 앱.
2. **실행 계정: 나(배포 계정)** — 사용자에게 시트를 직접 공유하지 않기 위해서다.
3. **액세스 권한**
   - 개인 계정 PoC: **나만** (현재 매니페스트 값). 다른 사람에게는 열지 않는다.
   - 조직 Google Workspace 승인 후: **도메인 내 사용자** 로 변경하고 `appsscript.json` 의 `access` 를 `DOMAIN` 으로 바꾼다.
   - **"Google 계정이 있는 모든 사용자" 또는 "모든 사용자"는 쓰지 않는다.** Google 공식 문서에 따르면 "나로 실행" 웹앱은 같은 Workspace 도메인이 아니면 접속자 이메일을 얻지 못할 수 있고, 이 시스템은 이메일을 모르면 모든 요청을 거부한다(fail closed). 즉 조직 외부 공개는 기능적으로도 쓸 수 없다.
4. 코드를 고친 뒤에는 "배포 관리 → 수정 → 새 버전"으로 다시 배포해야 웹앱에 반영된다.

### 5.2 사용자 등록
관리자로 웹앱 접속 → 사용자·권한 → 이메일·이름·역할 등록. 경매사는 기초자료 → 담당 경매사에서 중도매인별 담당 기간을 지정해야 해당 중도매인을 볼 수 있다.

### 5.3 권한 통제가 실제로 작동하는 곳

| 계층 | 구현 |
|---|---|
| 화면 | 역할에 없는 메뉴 숨김 (편의 기능) |
| 서버 함수 | 모든 `api_*` → `apiCall_` 에서 사용자·역할 확인, 중도매인 단위로 `requireWsAccess_` 확인. 클라이언트가 보낸 사용자·역할 값은 쓰지 않음 |
| 응답 필드 | `filter360ByRole_` 로 연락처·보증인 참조·증빙·이력을 서버에서 제거하고 전송 |
| 민감정보 | 보증인 상세는 별도 저장소, 별도 요청(`api_getGuarantors`), 조회할 때마다 `L_ACCESS` 기록 |
| 편집기 전용 | `setupSystem`·`loadVirtualData`·`runPipeline`·`restoreDb` 등은 소유 계정이 아니면 거부 |
| 저장소 | 파일은 소유 계정만 접근. `checkSecurity` 로 정기 확인 |

## 8. 알려진 한계

1. **집계는 매번 전체 재생성**한다. 가상 데이터 규모(원천 약 5만 행)에서는 문제없지만, 실자료가 커지면 6분 제한에 걸릴 수 있다. → 2단계에서 "변경된 월만 재계산"으로 바꾸는 것을 검토한다.
2. **원천은 연도별로 나누지 않았다.** 3년 이상 쌓이면 `DB_RAW` 를 연도별 파일로 나눠야 한다.
3. **데이터 상태의 "가져오기 문제"는 해당 실행에서만 반영**된다. 다음 정기 처리에서 문제 파일이 없으면 전체 상태는 정상으로 돌아오고, 문제 이력은 홈·가져오기 화면 목록에 남는다.
4. **잔액 연속성 점검은 원천 잔액이 "전기일 기준"이라는 가정**에 기대고 있다. 실제 원천의 잔액 산정 기준이 다르면 오탐이 생긴다. [확인 필요]
5. **반품·취소의 월 귀속**은 원거래번호가 있을 때만 원거래월로 옮긴다. 없으면 처리일 월로 집계하고 "경고"로 남긴다.
6. **한 번 승인한 버전은 취소 기능이 없다.** 잘못 승인했으면 바로잡는 새 버전을 등록해 승인한다(이력 보존 원칙).
7. **과거 시점 조회는 "유효기간" 기준**이다. "그 시점에 시스템에 무엇이 입력돼 있었는가"(입력 시점)까지 재현하려면 2단계의 판단 근거 스냅샷이 필요하다.
8. 웹 화면은 동시에 여러 사람이 무거운 조회를 하면 느려질 수 있다(조회마다 집계 시트를 읽음). 2단계에서 홈 대기열을 미리 계산해 둔다.
